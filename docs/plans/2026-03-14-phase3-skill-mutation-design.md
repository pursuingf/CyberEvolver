# Phase 3 Skill Mutation Design

**Goal:** Expand refiner phase 3 so it can create, modify, and delete content under `skills/`, while preventing deletion of `skills/skill_template`.

## Current Behavior

Phase 3 only allows `<create_file>` actions and enforces creation of exactly one new skill module. That blocks legitimate maintenance work such as updating an existing skill or deleting a stale one.

## Desired Behavior

Phase 3 should be the skill-tree mutation phase. It may:

- create new files under `skills/`
- modify existing files under `skills/`
- delete files or directories under `skills/`

Phase 3 must still reject:

- any path outside `skills/`
- unsafe paths such as absolute paths, parent traversal, or anything touching `submit.py`
- any deletion of `skills/skill_template` or paths inside that module

## Design

### Prompt Policy

Update the phase 3 hard constraints generated by `RefinerLLMClient._phase_policy_instructions()` so the LLM is told:

- it may use `<create_file>`, `<replace_code>`, and `<delete_file>`
- all edits must remain under `skills/`
- existing skills may be updated
- obsolete skills may be deleted
- `skills/skill_template` must not be deleted

### Validation

Update `RefinerLLMClient._validate_actions_for_phase()`:

- allow phase 3 action kinds `create_file`, `replace_code`, and `delete_file`
- keep the existing `skills/` path restriction
- remove the old "exactly one new skill module" validation
- add an explicit delete guard for `skills/skill_template` and any descendant path

### Testing

Add targeted tests for:

- replacing content in an existing skill file
- deleting a non-template skill file
- rejecting deletion of `skills/skill_template/...`
- rejecting phase 3 edits outside `skills/`

## Risks

- Phase 3 becomes more permissive, so prompt guidance needs to stay clear.
- Deleting directories is supported by `CodePatcher`, so the validator must guard both the module root and nested files for `skill_template`.
