# AutoPenBench Adapter Design

**Goal:** Integrate AutoPenBench into the current framework through a reusable benchmark adapter architecture, while keeping the first implementation focused on "run end-to-end" instead of broad platform refactors.

## Summary

The current framework assumes benchmarks are organized as:

- benchmark index JSON files under `benchmarks/`
- per-challenge `challenge.json`
- optional per-challenge `docker-compose.yml`

AutoPenBench uses a different layout:

- `data/games.json`
- `benchmark/machines/...`
- `benchmark/milestones/...`
- `benchmark/solutions/...`

Instead of adding `autopenbench`-specific branches throughout `ChallengeClient`, `challenge_server`, and prompt templates, the framework should introduce a benchmark adapter layer. AutoPenBench becomes the first non-`challenge.json` adapter, and future benchmarks such as CVE Bench or Xbow can plug into the same interface.

The first milestone is intentionally narrow:

- introduce a benchmark adapter registry
- let adapters emit a normalized challenge record and a generic `LaunchSpec`
- let `challenge_server` execute `LaunchSpec`
- add a `pentest_remote` prompt profile for AutoPenBench

Sandbox reorganization is explicitly deferred until the new benchmark can run successfully.

## Requirements

### Functional

1. The framework must load AutoPenBench challenges without converting the benchmark into the legacy `challenge.json` layout.
2. The framework must keep source benchmark semantics available instead of flattening them away.
3. The server/runtime path must not depend on hard-coded `autopenbench` conditionals.
4. The first prompt integration must match AutoPenBench's original agent setup closely:
   - original task text as the main user-facing task
   - reachable endpoint information added by runtime
   - no milestone or solution leakage to the agent

### Non-Goals For This Iteration

- full sandbox abstraction and documentation
- full support for every AutoPenBench subtask category on day one
- re-implementing AutoPenBench's Kali-hosted interactive driver inside the current framework
- redesigning the evolutionary system beyond what is needed to run the new benchmark family

## Design

### 1. Benchmark Adapter Layer

Introduce a new module, for example `benchmark_adapters/`, with these responsibilities:

- discover challenges from different benchmark formats
- normalize them into a common runtime shape
- preserve source benchmark fields
- generate `LaunchSpec`
- choose a `task_profile` for prompt rendering

Recommended structure:

- `benchmark_adapters/base.py`
- `benchmark_adapters/registry.py`
- `benchmark_adapters/challenge_json.py`
- `benchmark_adapters/autopenbench.py`

The core abstraction should separate three concepts:

- `benchmark_name`
  Example: `nyu_ctf`, `cybench`, `intercode_ctf`, `autopenbench`
- `adapter_kind`
  Example: `challenge_json`, `compose_catalog`
- `task_profile`
  Example: `ctf_local`, `pentest_remote`

This avoids encoding all benchmark behavior into one dimension such as `benchmark_family`.

#### Adapter responsibilities

Each adapter should provide:

- `discover()`
  Return normalized challenge entries keyed by challenge id
- `normalize_metadata(raw_entry)`
  Build a shared runtime shape while preserving source fields
- `build_launch_spec(challenge)`
  Describe how runtime should start the challenge
- `build_prompt_context(challenge, runtime_record)`
  Prepare prompt-specific metadata
- `get_task_profile(challenge)`
  Return the profile used by prompt rendering

#### Normalized challenge shape

The framework should expose a normalized challenge record with at least:

- `id`
- `benchmark_name`
- `adapter_kind`
- `task_profile`
- `name`
- `category`
- `description`
- `files`
- `flag`
- `flag_format`
- `full_path`
- `source_fields`

`source_fields` should preserve benchmark-native information instead of rewriting it away.

Examples:

- existing challenge-json benchmarks preserve fields like `box`, `internal_port`, `compose`, `reference`
- AutoPenBench preserves fields like `task`, `target`, `vulnerability`, `alias`, `level`, `vm`

#### AutoPenBench metadata mapping

AutoPenBench should load from:

- `data/games.json`
- `benchmark/machines/<level>/<category>/...`
- `benchmark/milestones/...`
- `benchmark/solutions/...`

For the first iteration, the normalized entry should keep:

- source task text
- target service name
- vulnerability label
- benchmark level/category/vm identity
- machine root path
- milestone and solution paths for evaluator-side use

Agent-facing metadata should remain minimal. Internal evaluator/runtime metadata can remain attached to the normalized challenge without being shown to the agent.

### 2. Generic LaunchSpec + Server Execution

`challenge_server` should stop assuming a single per-challenge compose file. Instead, it should execute a generic `LaunchSpec` generated by the active adapter.

Suggested `LaunchSpec` fields:

- `mode`
  `static` or `compose`
- `compose_files`
  Ordered compose files to materialize
- `target_services`
  Services that should be exposed to the agent
- `dependency_services`
  Services required for startup but not shown to the agent
- `runtime_patches`
  Patches applied without modifying source benchmark files
- `exposure_mode`
  Initially `host_ports`
- `healthchecks`
  Port or protocol probes needed to confirm readiness
- `cleanup_policy`
  Cleanup hints for instance shutdown

#### Server responsibilities

The server pipeline becomes:

1. Resolve challenge through the adapter registry.
2. Ask the adapter for a `LaunchSpec`.
3. Materialize runtime compose patch files.
4. Start containers with a generated project name.
5. Run health checks from `LaunchSpec`.
6. Return a runtime record with:
   - `status`
   - `project_name`
   - `target_info`
   - `adapter_kind`
   - `task_profile`

#### Why AutoPenBench needs runtime exposure support

AutoPenBench does not generally expose target services to the host. In the original benchmark, the agent operates from Kali on the internal network and reaches targets over `192.168.x.x`.

The current framework does not place the agent inside AutoPenBench's internal network in the same way. Therefore, the first integration must expose reachable host endpoints for target services.

This is the minimum runtime deviation required to make the benchmark runnable.

#### AutoPenBench launch strategy for iteration 1

The AutoPenBench adapter should produce a compose-based `LaunchSpec` that:

- includes the base machine compose
- includes the level/category compose
- targets the service named in `games.json`
- infers service dependencies from compose definitions
- removes fixed `container_name` values at runtime
- injects dynamic host port mappings for target services

Recommended exposure heuristics for the first milestone:

- `access_control`: expose `22/tcp`
- `web_security`: expose `80/tcp`
- `cryptography`: expose `8080/tcp`
- `real-world/cve`: prefer compose-defined ports, then Dockerfile `EXPOSE` hints

The first AutoPenBench milestone should prioritize categories that fit this model best:

- `access_control`
- `web_security`
- `cryptography`
- selected `real-world/cve`

More complex networking-heavy tasks can be added later without breaking the architecture because `LaunchSpec` already includes `exposure_mode`.

### 3. Prompt Organization By Task Profile

Prompt behavior should not branch directly on benchmark name. It should branch on `task_profile`.

Initial profiles:

- `ctf_local`
  Current framework default
- `pentest_remote`
  AutoPenBench profile

#### Prompt architecture

Keep one shared prompt skeleton and inject profile-specific guidance through rendering context.

The shared skeleton should continue to define:

- one-command-per-step formatting
- bash block requirements
- non-interactive execution constraints
- `submit` usage
- `load_skill` usage

The profile should define how the task is framed.

#### `pentest_remote` behavior

For AutoPenBench-style tasks:

- system prompt should frame the task as remote service exploitation rather than local artifact-first challenge solving
- instance prompt should use the original AutoPenBench task text as the main task description
- runtime should append reachable endpoint information from `target_info`
- files should only be shown if the benchmark actually provides local handout files

The agent should not see:

- milestone files
- solution files
- internal machine directory structure
- benchmark-private runtime metadata

This keeps the prompt close to the original AutoPenBench notebook behavior:

- a short system instruction
- the raw task text
- reachable target information

#### Template implementation direction

The current `gen0_root/skill_based` templates should not grow benchmark-specific hard-coded text. Instead, they should render against `task_profile`.

This allows:

- AutoPenBench to use `pentest_remote`
- existing benchmarks to stay on `ctf_local`
- future benchmarks such as CVE Bench or Xbow to reuse an existing profile or add a new one cleanly

Prompt sources should also be unified enough that changes to `gen0_root` and runtime configs do not drift apart silently.

## Scope For The First Running Version

The first implementation should optimize for getting a real AutoPenBench subset running inside the current framework.

### Include

- benchmark adapter registry
- legacy benchmark adapter for current challenge-json benchmarks
- AutoPenBench adapter
- generic `LaunchSpec`
- `challenge_server` execution path based on `LaunchSpec`
- `pentest_remote` prompt profile
- at least one working AutoPenBench category end-to-end

### Defer

- sandbox refactor
- full evaluator integration redesign
- exhaustive category support for AutoPenBench network-heavy tasks
- full benchmark-agnostic analytics/reporting changes

## Rollout Sequence

1. Introduce adapter registry and migrate current benchmark loading behind it.
2. Add `LaunchSpec` and refactor `challenge_server` to consume it.
3. Implement AutoPenBench adapter.
4. Add `task_profile` prompt branching with `pentest_remote`.
5. Smoke test a small AutoPenBench subset and verify launch, reachability, prompt rendering, and flag submission.

## Risks

### Runtime reachability mismatch

AutoPenBench was designed around an internal Kali vantage point. Host-port exposure may not be sufficient for every category.

Mitigation:

- start with categories that map cleanly to exposed TCP services
- keep `LaunchSpec.exposure_mode` extensible for later shared-network execution

### Prompt drift

The repository currently has both template files and config-based prompts.

Mitigation:

- anchor behavior to `task_profile`
- keep profile-specific wording centralized

### Adapter fragmentation

If adapters return ad hoc metadata, the abstraction will collapse quickly.

Mitigation:

- keep `NormalizedChallenge` and `LaunchSpec` explicit
- preserve source fields under a dedicated namespace instead of flattening everything

## Decision

Proceed with:

- adapter registry
- generic `LaunchSpec`
- `pentest_remote` prompt profile
- AutoPenBench integration focused on the smallest runnable subset

Defer:

- sandbox reorganization
- broad benchmark platform cleanup beyond what is needed to run the new benchmark path
